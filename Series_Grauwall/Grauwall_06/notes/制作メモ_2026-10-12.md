### 1-5. パイプライン（novelctl）の改修
| 変更 | 理由 |
|---|---|
| 校閲役を Aion から `claude-haiku-5.5` に変え、予備を `gpt-6-luna-pro` にした（OpenRouter の `models` 配列で自動切替） | CANON との整合・矛盾・誤字のチェックに、推論の時間とトークンを使いすぎていた |
| `.env` の `NOVEL_MODEL` が効く役を、書き手と磨きに限った（`model_env_roles`） | 審査役まで Aion で上書きされていた |
| Claude が書いた章を「渡された章」としてそのまま通す仕組み（`given_chapters`）を作った | Claude の第1〜3章を工程に乗せるため |
| 設計だけ推論を medium、締め切り900秒、`max_tokens` 64000 にした | Aion が推論6〜7万字を使い、本文が0字のまま時間切れになった。haiku は推論と CANON 本文で 32000 トークンを使い切った |
| 締め切りを過ぎたら、推論の深さを一段下げて投げ直すようにした | 同じ条件で投げ直すと、同じ時間切れを繰り返すため |
| **書き手を Aion から `claude-haiku-5.5` に、審査を `gpt-6-luna-pro` に変えた** | Aion は設計で3回とも審査不合格。発想も凡庸（プロデューサー判断） |
| 書き直しは「指摘された文と、その前後の一、二文だけ」直すようにした | 全文を書き直すたびに、新しい食い違いが出ていた |
| CANON 審査の推論を medium にした | low では推論が0字で、指摘が毎回入れ替わり、誤読もあった |
| その章で補強する伏線は「章カードの範囲だけ明かしてよい」とパケットに書くようにした | 第14章で「在りかを語れ」と「明かすな」が食い違った（ハーネスのバグ） |
| 章番号の漢数字を「二十」まで増やした | 20章の作品が初めてだったため |

## 2. 気づき

### 2-1. モデルの使い分け
- **Aion はボトルネックだった。**
  - 設計では推論の暴走と時間切れが続いた。
  - 3回とも審査で不合格だった。
  - Novel_5 のコンペでも、出てくる案は凡庸だった。
- **普及価格帯のモデルで執筆も審査も十分だった。**
  - haiku-5.5 と luna-pro。
  - 本文の文体は、ライターが交代した継ぎ目（第3章→第4章）に違和感が出ない水準だった（プロデューサー確認）。
- **luna-pro は審判として優秀だった。**
  - 数字・呼び方・視点の破れを正確に拾う。
  - 筋を変えない報告書やレポートの文字チェック・整合チェックなら、luna-pro で十分。
  - そこに GPT-Sol や Opus を使うのはオーバースペック。追加提案が増えて、人の判断が迷走する。
- **安い審判の弱点は三つあった。**
  1. 資料の外の常識を拾えない（20里先で街の鐘が聞こえる、など）。
  2. 指摘の重さの付け方が粗い。
  3. 審査を回すたびに見る場所が変わり、収束しない。
- **安いモデルは「全体の整合を取りながら直す」のが苦手。**
  - 指摘を一つ直すと、別の場所に齟齬が出る。
  - 「全体の設計をこう見直して」と言わないと直らない。
- **分担の結論：**
  - 書く・照合するのは安いモデルで、何度でも回す。
  - 全体の整合を直す・常識で確かめるのは上位モデルで、1回だけ。
  - 止めるかどうかは人が決める。
- **実績（第6回）：**
  - 上位モデル（Claude）が入ったのは、設計の修正2回、章の手直し5回、校正1回。
  - 残りの約90回の呼び出しは安いモデル。
  - 費用はドル単位にも届かない。

### 2-2. 物語を作るハーネス
- novelctl の価値はモデルではなく「型」にある。
  - BRIEF/CANON の契約
  - 台帳（LEDGER）
  - 書き手と審査役の分離
  - 人の承認の関門
  - guard の封印
  - Claude が書いた章を渡す仕組み
- 同じ事実が二か所に書かれていると、必ず食い違う（革紐の扱い、到着時刻、ケガ）。
- CANON に「書いてあること」は守られる。「書いていない世界の前提」は、安いモデルが現代の常識で埋めてしまう（鐘、指の数、屋内か屋外か）。
- 足したルールには「どこで効くか」の範囲が要る。刻み蝋燭が山の石段（屋外）に出てきたのがその例。
- 章をまたいで、人物の口調が少しずつずれていく（ケスの敬語、トマスの「っす」、エーリカの丁寧語、ダリオ）。
- 台帳（記録係）の誤りが、最終審査を汚した。本文が正しく、台帳が間違っていた。
- 「指で数える」のような普遍の前提は、種族の体から決まる。決めていないと、書き手が人間の体を当てはめる。

### 2-3. 運用の小さな教訓
- device bridge の staging は、VM で書いたファイルを hardlink として拒否する。公開リポジトリの origin から取り、編集をやり直して sha1 を照合する回避策が有効だった。
- 存在しないコマンド（`next`）を案内してしまった。手順書（KICKOFF.md）の正しいコマンドを確かめてから案内する。
- ステータス表示だけでは「再実行されたか」が分かりにくい。最後のログの行で確認する。

## 3. アイデアの種（このチャットで出たもの）

### 3-1. サービス・プロダクト
1. **封をした正典（ネタバレなしで特等席）**
   - 利用者は、ジャンル・発散の具合・終わり方・出力形式（小説／ゲームシナリオ／動画台本）を選ぶ。
   - AI のプロデューサーが、真相を含む正典を作って封印する。
   - 利用者に見せるのは、キャッチコピーとリード（あらすじ）だけ。
   - 「読みたい」と思ったときだけ本編を生成する。重い処理は買う気が確定してから走るので、費用の形が良い。
2. **予告編ファーストの平台**
   - 普及価格帯のモデルを5社ぶん並べ、5倍の案を出させる（多様性）。
   - 本屋の平台のように10冊並べて選ばせる。
   - 客層は、表紙・タイトル・リードで買う人や、予告編で映画を観る人（アーリーアダプター）。
3. **約束の検証と回収の保証**
   - 封印の前に「このリードの約束を、この正典で回収できるか」を審査する。
   - 回収されなかった伏線を台帳で検出して、返金や再生成をする。
   - 「最後まで破綻しない」ことを保証として売る。
4. **公開棚**：一点ものの作品を公開できるようにして、口コミで選ぶ人にも届ける。生成した人が、そのまま発信者になる。
5. **一つの正典から複数の媒体へ**：同じ封印済み正典から、小説、ゲームシナリオ、動画台本を出す。
6. **卒論向けの整合支援**：本人が書いた原稿の構成・用語・引用の整合を管理する道具（本文の代筆はしない）。
7. **なろうの有料機能**：破壊力はあるが、投稿サイトの足場を崩す。外部が先にやる可能性が高い。
8. **照合専用の校閲エンジン**
   - 照合する資料と、指摘の重さの基準を設定ファイルで固定する。
   - 提案はしない。「どこが、どの資料のどこと食い違うか」だけを返す。
   - 使い道：契約書×社内規程、手順書×構成定義。
9. **モデルの採用試験**：同じ BRIEF で複数のモデルに設計させ、審査点・試行回数・費用を自動で比べる。社内向けのモデル評価基盤にもなる。
10. **紋章ジェネレーター**：架空の組織の紋章を、本物と偽物の対で作る（今回の刺繍の描き分けから）。
11. **表紙の「違い探し」企画**：毎回の表紙に、本文とつながる小さな違いを一つ隠す。読者が感想欄で答え合わせをして、回遊のきっかけにする。

### 3-2. ハーネス・エージェント設計
1. **例外処理だけ高級品**：上位モデルは「書く」ではなく「止まったところを一度で直す」に使う。費用の設計図になる。
2. **役ごとの LLM ルーティング部品**：設定ファイル1枚で、役と予備の順番を宣言する。AIOps の障害要約と照合にも、そのまま使える。
3. **推論の暴走の検知と段階的な縮退**：推論の文字数が伸びても本文が0のままなら「堂々巡り」と判断し、推論の深さを下げる・資料を分割する。
4. **設計の二段化**：骨組み（動機・旅程・章の役目）を短く出させて審査し、通ってから章カードを足す。枠切れも差し戻しも部分だけで済む。
5. **差分審査（収束が保証されるループ）**：指摘を台帳に積み、直った項目は再審査しない。新しい指摘は「前回の修正が原因のもの」に限る。
6. **停止条件の設計**：自動の審査がいつまでも通らないとき、どこで人の判断に切り替えるかを決めておく。AIOps の変更承認フローと同じ形。
7. **事実の表と章カードの分離**：事実は表に一か所だけ置き、章カードは表を引く。同じ事実が二か所にない構造にして、食い違いを原理的になくす。
8. **数字の照合は機械に**：金額・里程・刻の合計は、CANON から表を抜き出して計算で照合する。審判は筋に集中させる。
9. **世界の物理表**：音の届く距離、歩く速さ、灯りの見える範囲を表にして、審判に照合させる。
10. **ルールの適用範囲（スコープ）タグ**：屋内か屋外か、城壁の内か外か、どの章かを付けて、その場面に当たるルールだけを渡す。
11. **学習するテンプレート**：止まるたびに足した前提を「よく破られる前提」として記録し、次の作品の CANON ひな形に入れる。障害の振り返りを、次の手順書に織り込むのと同じ。
12. **人物と場所のカード**：確定した章から口調と場所の構造を抜き出して、毎回のパケットに添える。
13. **台詞の指紋（キャラ崩れ検知器）**：人物ごとに、文末・一人称・呼びかけ・台詞の長さを確定章から抜き出し、新しい章と比べてずれを警告する。
14. **継ぎ目の可視化指標**：章ごとの文体特徴を数値化して並べ、ライターの交代が「見える」かどうかを測る。共同執筆 AI の品質保証になる。
15. **台帳の再生成**：台帳は本文から機械的に作り直せる形にして、最終審査の前に一括で再生成する（ログの正しさを先に保証する）。
16. **「もしかして」**：存在しないコマンドを受けたら、近いコマンドを提案する。人とエージェントが同じ CLI を叩く運用ツールで、事故を減らす。

### 3-3. 世界観・物語
1. **体の違い → 制度の違い → 誤解 → 事件**
   - 蜥蜴人の市場は八を一まとまりにして値をつけるので、人間との取引で揉める。
   - 鴉人の伝令は「群れほど来た」としか報告できないので、隊長が人数を読み違える。
   - 系統A の短編の種として何本も作れる。
2. **人間の暦・通貨は人間の体が基準**（十本の指、二十本の手足の指）。「見分けない街」という主題と静かに響き合う。
3. **異種族の体の監査**：指の数、眠る時間、食べられるもの、温度の感じ方、文字を読めるか。人間を基準にした設定の中で、人間でない者が人間の体で動いている箇所を見つける。
4. **絵から設定を決める**：表紙の刺繍がそのまま正典になった。小道具や紋章は先に絵を描き、絵と文の両方を正典にする。
5. **ネタバレなしで特等席の課題**：今はプロデューサーが真相を知っているので、特等席ではない。「作り手の役をどこまで AI に渡すと、読み手として驚けるか」が次の設計の問い。
