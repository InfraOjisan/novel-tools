## はじめに

[1本目](./ai-novel-studio-metaharness)で制作スタジオの組み方を、[2本目](./ai-novel-studio-part2)で書き手のAIの選び方を、[3本目](./ai-novel-studio-part3)でシリーズの設計を書きました。今回は、その続きの一番地味な工程、**書き終えた小説を実際に公開する**ところです。

完成した2作を「小説家になろう」に出しました。

| 作品 | 元原稿 | なろうでの話数 |
|---|---|---|
| 銀の川をのぼる（SF） | 校正済みの1本のmd（約2万字、8章） | 全8話 |
| 夜啼きの涙（ファンタジーの叙述ミステリ） | 1本のmd（約4.6万字、7章） | 全14話（1章を前編・後編に分割） |

公開サイトに出す作業は、操作そのものは単純です。ただ、手でやると事故ります。章をコピペし間違える、同じ話を二重に公開する、サブタイトルを取り違える。しかも公開は取り消しにくい。そこで、**下書き保存、読み戻し検証、人間の承認、公開、公開後の照合**までをスクリプトにして、他のAIエージェント（GooseやHermes）が繰り返し実行できる手順書も添えました。

この記事は、そのとき考えたことと、実際に踏んだ穴の記録です。

## 先に結論

- 日本の小説投稿サイトに、**公式の「投稿API」は見つけられませんでした**。なろうのAPIは検索・取得だけです。現実的なのは、ブラウザの自動操作です
- 自動操作は、**「探索はAIに、繰り返しはスクリプトに」**分けると安定します。画面の仕様をAIに調べさせ、見つけた入力欄とボタンを決まった手順に固めました
- 公開は、**人間のOKが出るまで下書きで止める**。下書きは、なろう側から読み戻して原稿と完全一致を確認してから見せる
- ログインだけは**人間が行う**。パスワードはスクリプトにもAIにも渡さない
- 公開できたかは、**読者が見るページ**で確かめる。管理画面の「投稿済み」では足りない

## 全体の流れ

```text
Novel_N/output/final.md（章ごとに「## 第N章　題」）
   │  prepare.py   … 5,000字以内に分割し、out/ に本文と manifest.json を出力
   ▼
out/Novel_N/001.txt … + manifest.json（サブタイトル・字数・sha1）
   │  post.mjs draft    … なろうに「下書き保存」→ 編集画面から読み戻して原稿と照合
   │  post.mjs verify   … 下書き全話をもう一度照合
   ▼
 （ここで人間に報告。OKが出るまで公開しない）
   │  post.mjs publish --yes … 話数順に公開
   │  post.mjs check         … 読者向けページの本文と原稿を照合
   ▼
 完了（Nコードと各話のURLを報告）
```

ファイルは、小説ツール一式のリポジトリの `publish/narou/` に置いています（[novel-tools](https://github.com/InfraOjisan/novel-tools)）。変換は標準ライブラリだけのPython、投稿はNode.jsの `playwright-core`（Playwrightのコア部分）で、Macに入っているGoogle Chromeを使います。ブラウザは別途ダウンロードしません。

## 1. まず、仕様は「AIに探索させる」

なろうの投稿画面は、手順に慣れないと読めません。ここは、AIにブラウザを操作させて調べました。やらせたことは次のとおりです。

1. ログイン後、作品作成の画面、作品設定、話の新規作成、公開の確認までを順にたどる
2. 各画面の入力欄の名前、ボタンの文言、遷移先を記録する
3. 公開の直前で止める（確定ボタンは押さない）

そこでわかった仕様が、スクリプトの前提になっています。

- 作品の新規作成は**タイトルだけ**を入れて「保存する」。この時点で作品IDが発行され、作品は未公開
- 作品設定で**「AI利用状況」を選ばないと投稿できません**（不使用、補助的利用、間接利用、直接使用の4択）
- 話の本文は**200字以上70,000字以内**。5,000字という数字は、サイトの制限ではなく**僕の運用上の上限**でした
- 話の登録は「下書き保存」。公開は、下書きの詳細ページから「投稿」を押す別の操作

最後の点が効きます。**下書き保存まで進めても、読者には見えません。** だから、人間が確認する場所を、公開の手前に置けます。

探索で見つけた画面の情報は、手順書（`RUNBOOK.md`）の「画面メモ」に書き残しました。サイトが改修されたら、ここを基準に直します。

## 2. 5,000字以内に分ける

1作目は1章が約2,500字なので、そのまま1章を1話にできます。3作目は1章が約6,400〜7,700字あり、5,000字を超えます。そこで、**場面区切り（`＊`）で前編・後編に分ける**ことにしました。

分割は次のように決めています。

- 全体の字数から、必要な分割数を求める
- 目標の位置に最も近い**場面区切り**で切る。場面区切りが近くになければ、最寄りの段落境界で切る
- 切り口の `＊` は、前後の話の先頭・末尾から落とす
- すべての話が5,000字以内に収まらなければ、分割数を増やして再計算する

```python
# 目標位置に最も近い「場面区切り」を優先して切る（抜粋）
scene = [i for i in cands if SCENE_BREAK.match(blocks[i].strip())]
pool = [i for i in scene if dist(i) <= total * 0.2] or cands
cuts.append(min(pool, key=dist))
```

結果は、7章が14話になり、各話は約2,800〜4,400字でした。分けたときに一番怖いのは**文章が落ちること**です。そこで、「分割後の全話を連結した本文」と「元のmd（見出しと区切り記号を除く）」を突き合わせ、完全一致を確かめました。

## 3. ログインは人間、スクリプトはCookieだけを使う

`.env` にはなろうのIDとパスワードを置いてありました。それでも、**スクリプトはそれを読みません**。

- AIエージェントが、パスワードを入力してログインすることはしない。人間の担当にする
- 代わりに、スクリプト専用のChromeプロファイル（`.chrome-profile`）を作る。最初の1回だけ `node post.mjs login` で窓を開き、**人間がログイン**する
- 以降は、そのプロファイルの**ログイン状態（Cookie）**を再利用して、画面を出さずに（`--headless`）動かせる
- プロファイルはCookieを含むので、`.gitignore` に入れてコミットしない

```javascript
const ctx = await chromium.launchPersistentContext(PROFILE, {
  channel: 'chrome',            // 手元のGoogle Chromeを使う（ダウンロード不要）
  headless: flag('headless'),
  locale: 'ja-JP',
});
```

副作用ですが、**同じプロファイルは同時に2つ起動できません**。このことが、あとで効いてきます。

## 4. 下書き保存は「読み戻して」確かめる

下書きの保存後、ブラウザが保存画面に遷移したら成功、とは考えませんでした。**保存された内容を、なろうの編集画面から読み出して、手元の原稿と比べます**。

```javascript
async function readDraft(page, draftId) {
  await page.goto(`${BASE}/draftepisode/updateinput/draftepisodeid/${draftId}/`);
  const subtitle = await page.inputValue('input[name=subtitle]');
  const body = (await page.inputValue('textarea[name=novel]')).replace(/\r\n/g, '\n');
  return { subtitle, body };
}
// 保存直後に比較。1話でも違えば、その場で止める
const ok = got.subtitle === ep.subtitle && got.body.trim() === ep.body.trim();
```

入力欄に貼ったあとの画面の文字数カウンタも、手元の字数と比べています。

結果は、全22話が一致でした。1作目の8話、3作目の14話の全話を、さらに別のコマンド（`verify`）で再照合しています。

登録済みかどうかは、**サブタイトルで判定**します。同じコマンドを何度流しても、登録済みの話は飛ばすので、二重に保存しません。途中で止まっても、再実行すれば続きから進みます。

## 5. 公開は人間のOKのあとにだけ

下書きが全話そろった段階で、いったん人間に渡します。僕は1作目の第1話を自分の画面で公開し、内容を確かめました。そのうえで「残りも公開してください」と指示しました。

スクリプト側も、うっかり公開しないように作っています。

- `publish` は `--yes` を付けないと動きません
- 公開の直前に、**もう一度**下書きを読み戻して原稿と照合する。不一致なら中止する
- `--only=3` のように、1話だけ試せる

この `--only` が役に立ちました。

### 公開は「2段階」だった

最初の公開の試行は失敗しました。下書き詳細の「投稿」を押すと、画面遷移なしに出るダイアログが、次の順で変わります。

1. 「投稿」→ 予約掲載の設定と代表作の設定のダイアログ
2. 「投稿[確認]」→ **同じダイアログの中で、ボタンが「投稿[実行]」に切り替わる**
3. 「投稿[実行]」→ 「投稿が完了しました」

僕のスクリプトは、2段階目を想定していませんでした。そこで、スクリプトの動作を一度止めて、**同じ手順を画面で手動でたどり**、2段階目のボタンを見つけて直しました。

```javascript
await page.getByRole('button', { name: /投稿\[確認\]/ }).click();
const exec = page.getByRole('button', { name: /投稿\[実行\]/ });
await exec.waitFor({ state: 'visible', timeout: 20000 });   // 同じ画面内で切り替わる
await exec.click();
await page.getByText('投稿が完了しました').waitFor({ state: 'visible' });
```

直したあとは、**1話だけ**公開して確かめ、残りの話を進めました。いきなり全話を流していたら、と思うと、「まず1話」の運用は妥当でした。

### ツールの応答が途切れたとき

最後の作品の公開中、AIの操作ツールが「Macから応答がない」と返してきました。このとき、**スクリプトは裏で動き続けていました**。ここで慌てて公開コマンドを再実行すると、二重公開になりかねません。

やったことは次のとおりです。

1. 再実行せず、プロセスを確認する（`ps` で `post.mjs` を探す）
2. 状況確認のコマンドを流したら、プロファイルが使用中と出た。これで、前のスクリプトがまだ動いていると確認できた
3. プロセスの終了を待つ
4. 終了後に状況を確認する

結果は、全話の公開が正しく完了していました。プロファイルの排他が、図らずも「今も動いている」ことの目印になりました。この失敗の対処は手順書に書いてあります。

## 6. 公開できたかは「読者のページ」で確かめる

管理画面の話一覧に「投稿済」と出れば、公開されたと見なせそうです。でも、**読者が見るページに、本文が正しく出ているか**は別の問題です。そこで、公開後に別のコマンド（`check`）で次を行います。

1. 管理画面から、読者向けの**Nコード**を取得する（作品ページのリンクにあります）
2. `https://ncode.syosetu.com/<Nコード>/<話数>/` を開く
3. 本文の領域（`.js-novel-text`）のテキストと、サブタイトルを、手元の原稿と比べる。空白と改行は無視して比較する

最初に作った確認処理は、管理画面のリンクをそのまま開いてしまい、読者向けのページではありませんでした。全話が「不一致」と出て、**確認処理のほうが間違っていた**と気づきました。直したあと、全22話が一致しました。

| 作品 | 結果 |
|---|---|
| 銀の川をのぼる | 全8話の本文とサブタイトルが一致 |
| 夜啼きの涙 | 全14話の本文とサブタイトルが一致 |

## 7. 規約と申告：AIで書いた小説を出すときに決めたこと

### AI利用状況は、実態に合わせて申告する

作品設定の「AI利用状況」は、必ず選びます。選択肢は次の4つです。

| 選択肢 | 意味（サイトの説明の要点） |
|---|---|
| 不使用 | 創作にAIを使っていない |
| 補助的利用 | アイデア出し、資料調査、誤字脱字の確認など。何を書くかはAIが決めていない |
| 間接利用 | AI生成物を下書きや素材として間接的に使っている |
| 直接使用 | 本文に、AIが生成したテキストをそのまま使っている箇所がある |

この2作は、本文をAIが書いたものをほぼそのまま掲載しているので、**直接使用**を選びました。人間がノーチェックかというとそうではなく「ここはこう変えて」「この表現は不自然だからこんな感じに直して」と細かな注文はつけています。ただ書いているのも修正しているのもAIです（そういう実験なのです）。この判断は、僕が選びました。AIは選択肢を示すだけにしています。補足欄には、どのモデルがどの工程を担当したかを書いています。

### 他サイトとの重複投稿はよいか

僕が読んだ範囲では、なろうのヘルプは、他サイトとの重複投稿を特に制限していません。ただし、**あらすじに「他サイトにも掲載している」旨を書く**ことを求めています。書かないと、盗作や無断転載として通報されることがあるそうです。

縦書きの電子書籍を読めるサービスの[Romancer](https://romancer.voyager.co.jp/)にも載せたいので、併載の一文とURLをあらすじに足しました。これも手順書に載せています。

- RomancerのURLは、**公開の指示と一緒に指示者が渡す**。指定がなければ、**確認する**（推測しない）
- あらすじにすでに `Romancer` と書いてあれば、追記しない
- 注意：あらすじ内のURLは**クリックできない文字**として出ます。しかも一覧では途中が「…」で省かれ、「続きを読む」を開くと全体が出ます

### 宣伝はどこまでよいか

EPUBを無料で提供しているので、その告知をプロフィールと活動報告に書きました。なろうの公式ヘルプでは、個人による無料配布の告知は許可されています。禁止されているのは、**作品の本文欄での宣伝**、サンプルだけを出して続きに誘導すること、アフィリエイトリンク、企業による商業宣伝です。「無料で広告がないから商用ではない」と理屈を組み立てなくても、規約で許可されている範囲に収まっていました。

なお、これらは僕が公式ヘルプを読んだ範囲の理解で、法的な確認ではありません。自動操作そのものについての明示的な規約は、僕は確認していません。自分のアカウントで、2〜3秒間隔で、人間が行う操作と同じことを繰り返しているだけですが、真似をする方は、ご自身で規約を確認してください。

## 8. 小さな落とし穴

| 起きたこと | 対処 |
|---|---|
| 接続したフォルダが空だった（実際の置き場所は、別のパスだった） | 実際のパスを教えてもらい、そのフォルダにアクセスを許可した |
| すでに空の下書き作品が1件あった | 勝手に使わず、再利用するか新規作成するかを、人間に確認した |
| サンドボックスのgitが、リポジトリの `.git` 内のロックを削除できなかった | 原因はファイル削除の権限。ロックと一時ファイルは、削除できるMac側で片付けた。**サンドボックスから、共有フォルダのgitを操作しない**運用が安全 |
| 段落の間の空行は、なろうの画面でもそのまま空行として表示される | 段落ごとに空行を1つ入れたまま出した。読み味が横書きでどう変わるかは、次の節で |
| 作品の「完結設定」が「連載中」のまま | 作品の設定を勝手に変えず、人間に確認する。手順書の「公開後に人間が確認すること」に入れた |

## 9. 横書きでは、頭に入ってこなかった

公開した小説を、なろうで読んでみた感想です。**今回のような小説然とした文章は横書きで読むとラノベにあるような躍動感がなく、頭に文章が入ってきづらい**と感じました。なろうのWeb表示には、読者が選べる縦書き設定が（調べた範囲では）ありません。公式の縦書きPDF機能と、読者側のブラウザ拡張に頼ることになります。

そこで、縦書きのEPUBを無料で提供し、縦書きで読めるRomancerにも併載しました。実験としておもしろいのは、**同じ原稿を横書きと縦書きで出して、読まれ方の差を測れる**ことです。次の作品からは、執筆指示書（BRIEF）に「横書き向け」と「縦書き向け」の区分を入れて、文体を変える案も考えています。

## 10. エージェント向けの手順書にしておく

この作業は、今後も繰り返します。そこで、GooseやHermesのような別のAIエージェントが、同じ手順をそのままたどれるように、手順書（`RUNBOOK.md`）にしました。内容は次のとおりです。

- **守ること**（エージェント向けの規則）
  1. パスワードを入力しない。ログインは人間が行う
  2. 公開は、人間の明示的なOKのあとにだけ行う
  3. AI利用状況の申告は、人間が決めた値のまま変えない
  4. 作品の削除と、アカウント設定の変更はしない
  5. 想定外の画面やエラーが出たら、リトライを重ねず中断して報告する
- 通常フローのコマンド列、終了条件、報告に含めること
- トラブルと対処の表（「ツールの応答が途中で切れた」も入れてある）
- 画面メモ（入力欄の名前、ボタンの文言、URL）

「やっていいこと」と「人間に戻すこと」を、手順書の最初に書いておくのが、一番効きました。AIは書いてあることを守ります。逆に、書いていないことは、善意で先に進みがちです。

## これから

- **Romancerへの自動投稿**は、近日公開予定です。今回のなろう向けのスクリプトと同じ形（下書き、読み戻し、人間の承認、公開、照合）で作ります
- **サイト別の差**（AI申告のルール、本文の記法、ルビの形式）を、サイトごとの接続部分に閉じ込めて、同じ原稿から複数のサイトに出せるようにしたいと考えています
- **読者の反応の回収**：章ごとの評価やコメントを集めて、1本目で書いた「琴線マップ」につなげる

## まとめ

- 日本の小説投稿サイトには、**公式の投稿APIが見つからなかった**。現実的なのは、ブラウザの自動操作
- **探索はAIに、繰り返しはスクリプトに**。AIに画面の仕様を調べさせて、見つけた手順を決まった形に固める
- 公開の手前に**下書き**がある。そこで、**読み戻して原稿と完全一致を確認**し、人間に渡す

- AI利用状況は、**実態に合わせて、人間が決めて**申告する。重複投稿は、あらすじに書く
- 手順書の最初に、「やっていいこと」と「人間に戻すこと」を書く
