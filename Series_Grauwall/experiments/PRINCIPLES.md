# PRINCIPLES.md — 小説工房から抽出する原理（業務AI統制の演習場として）

シリーズ全体で使う。話ごとの記録（`experiments/epNN/`、各作業フォルダの `notes/INTERVENTIONS.md`）から、ここへ抽象化して積む。

## 0. この工房の目的
- 小説工房は、**業務 AI の統制を試す演習場**である。小説家を目指しているわけではない。
- 検証する仮説：**普遍的にすべての業務に AI は使えるのではないか（≒人間をどこまで最小化できるか）**。
- 得た知見を抽象化して原理・法則にする。急激な人口減少が始まった日本の業務に持ち帰れる知見にする。
- 小説を題材にする理由：AI が逸脱しても実害がない。それでいて、承認抜け・共謀・規則の抜け穴・作話といった事故の形は、業務と同じものが再現される。

## 1. 業務の型
会社の業務（日々の営み）のほとんどは、次の型に入る。小説工房は、この型をそのまま持ち込んだもの。
1. 台帳を作り、固定する（＋監査ログ）
2. 変更・追加・削除は承認を要する。申請には **理由・目的・根拠・影響** を明らかにする
3. 承認された変更を台帳へ反映し、再固定する（＋監査ログ）
4. 定期的に台帳を **棚卸し** する

| 業務の型 | 小説工房での実装 | 状態 |
|---|---|---|
| 台帳の作成と固定 | CANON.md のロック、SERIES_LEDGER、guard の seal（sha256） | あり |
| 監査ログ | git の履歴、`notes/INTERVENTIONS.md` | あり |
| 変更の申請と承認 | 差し戻し（`work/canon_feedback.md`）、`approve-canon`、seal は人の仕事 | あり。**申請に「影響」欄がない**（どの章・どの設定に波及するかを書かせていない） |
| 反映と再固定 | 再設計 → 再ロック | あり |
| 棚卸し | — | **なし**。話と話の間に、公開済みの本文と SERIES_LEDGER を突き合わせる工程を足す |

## 2. 責任とリスクの分解
責任もリスクも、次の要素で分解・分類・整理して明確にする。**グレーゾーン（誰が持つか決まっていないもの）は許さない。**

| 要素 | 意味 |
|---|---|
| 回避 | 事前にやらない・置かない |
| 委任 | 権限を渡す。責任は委任元に残る |
| 譲渡（移転） | 責任ごと相手に移す（契約・保険など） |
| 転嫁 | 負担を他へ回す |
| 受容 | 委任・移転・転嫁で必ず残る責任やリスクを、自分で受け止める |

**「リスク受容」は最後の話。** 気軽に使う言葉ではない。先に回避・委任・移転・転嫁で分解し、それでも残ったものだけを、誰が受容するかを名指しで決める。

### 2-1. 小説工房に当てはめる（暫定。話を重ねて直す）
- 回避：秘密を作業フォルダに置かない（GOVERNANCE 層1）。実在の人物・他作品の模倣を企画で禁じる。汚れた回（第3回・混成チーム）は打ち切って採らない。
- 委任：執筆・審査・検査を AI（Aion、Hermes のチーム、Claude）に渡す。
- 移転：いまはない。移転先は責任を負える主体（人・法人）に限られる。
- 転嫁：こちらは**受ける側**にいる。モデル提供者の規約は出力の責任を利用者へ、公開先の規約（Romancer の公開時の確認）は内容の責任を作者へ回している。
- 受容：プロデューサーに残る。公開の承認、規約への同意、seal、guard で減らしきれない引き写しの残余。

### 2-2. 原理の候補
1. **いまの制度の下では、AI には委任しかできない。** AI は責任を負える主体として扱われていないので、移転も転嫁も AI には向けられない。AI に渡した仕事の責任は、すべて委任元に残る。「AI がそう答えたから」は、受け手のいない転嫁で、無効。責任は言った本人の受容に落ちる。
2. **人間を減らせる下限は、AI の能力ではなく責任の所在で決まる。** 能力で決まる部分は時間とともに削れる。責任で決まる部分は、制度が変わらない限り残る。
3. **効くのは、受容する一人が承認だけで回せる範囲を広げること**（承認一回あたりの業務量）。検査の層（guard・審査・台帳の欄）は、受容する量を小さくする道具として位置づける。
4. **ただし、AI が責任を負う世界はありうる（仮説）。** 火も火薬も自動車も飛行機も核も、「便利で必要な道具で、ない世界には戻れない」から、人間は責任を引き受ける形を作って使い続けてきた。AI を特別視する必要はない。法整備が追いつかないまま利用が進む（自動運転のように）のも同じ道筋で、いつか誰かが落としどころに到達する。
   - 落としどころの前例：法人（人でないものを責任の主体にした最大の前例。財産で裏づける）、自動車の強制保険と運行供用者の責任（過失を問わず、決まった者が払う仕組み）、原子力の責任集中（事業者に集め、国が後ろを支える）。
   - 共通する形：**名指しできる主体（登録）＋ 払う財源（資産・保険・供託）**。AI に責任を負わせる制度も、この形になる見込みが高い。財源の出どころは最後は人間なので、第2節の「最終的に人間が引き受ける」とは矛盾しない。

## 3. 介入の分類（`notes/INTERVENTIONS.md` のタグ）
人が手を出した記録が、この演習場の主な観測データ。各介入に二つのタグを付け、話ごとに数えて、どの種類が減りどれが残るかを並べる。

**種類**
| タグ | 中身 | 見込み |
|---|---|---|
| 環境 | 起動、push、ログイン、設定値の変更 | 手間であって判断ではない。仕組みで消せる |
| 調停 | 止まった場を動かす、次に誰が動くかを決める | 役割として設計すれば AI に寄せられる可能性 |
| 妥当 | 成り立つかの判断（冬に隊商は出ない、報酬の出どころ） | 能力の問題。強いモデルと台帳の欄（理由・財布）で減る |
| 責任 | 承認、規約への同意、seal、公開 | 制度が変わらない限り残る |

**責任の扱い**：回避／委任／移転／転嫁／受容（第2節）

## 4. 観測された実例
- 第3回・混成チーム：承認を通さない台帳の変更（他作品のプロットの混入）が、記録されないまま流れかけた。業務でいちばん起こしてはならない事故と同じ形。気づけたのは見張り役だけ。→ `experiments/ep03/OBSERVATIONS.md`
- 第3回・Aion：設定の妥当性の問題を、人が二度差し戻した。Aion 自身の審査は、整合（台帳と本文の食い違い）は拾えたが、妥当（そもそも成り立つか）は拾えなかった。→ `Grauwall_03_aion/notes/INTERVENTIONS.md`
